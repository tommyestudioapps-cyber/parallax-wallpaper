# Proposta de instrumentação — diagnóstico do primeiro frame após retomada

## Objetivo

Não alterar a lógica do Parallax, a frequência do sensor, o cálculo do movimento, o carregamento das imagens ou a arquitetura de threads neste momento.

A finalidade desta etapa é **medir com precisão onde o primeiro frame após `visible=true` está consumindo tempo**.

O log atual mostra:

```text
visible=true
→ sensor registrado
→ DRAW_START
→ LOCK_CANVAS_SUCCESS
→ aproximadamente 400 ms
→ DRAW_COMPLETE
```

Porém, atualmente `DRAW_START` é registrado **depois de `prepareComposition()`**, e `DRAW_COMPLETE` só ocorre depois de `unlockCanvasAndPost()`.

Portanto, precisamos subdividir essas regiões.

---

# 1. Instrumentar `prepareComposition()`

Adicionar timestamps/logs antes e depois de cada etapa importante.

A sequência desejada é:

```text
PARALLAX_PREPARE_START

PARALLAX_COMPOSITION_JSON_READ_START
PARALLAX_COMPOSITION_JSON_READ_END

PARALLAX_RECYCLE_START
PARALLAX_RECYCLE_END

PARALLAX_BITMAP_LOAD_START index=0
PARALLAX_BITMAP_LOAD_END index=0

PARALLAX_BITMAP_LOAD_START index=1
PARALLAX_BITMAP_LOAD_END index=1

PARALLAX_BITMAP_LOAD_START index=2
PARALLAX_BITMAP_LOAD_END index=2

PARALLAX_PREPARE_END
```

Preferencialmente, cada log deve conter também a duração em milissegundos.

Exemplo:

```text
PARALLAX_BITMAP_LOAD_END index=0 durationMs=123
```

Isso permitirá descobrir se o custo ocorre durante:

* leitura do SharedPreferences;
* parsing do JSON;
* `recycle()`;
* abertura do `InputStream`;
* `BitmapFactory.decodeStream()`;
* `BitmapFactory.decodeFile()`.

### Importante

Não modificar a lógica de `prepareComposition()`.

A instrumentação deve apenas medir.

---

# 2. Mover/duplicar a medição para deixar claro onde `DRAW_START` realmente começa

Atualmente:

```java
private void drawFrame(boolean force) {
  prepareComposition();
  boolean logFrame = shouldLogFrame(force);
```

Isso faz com que o tempo de `prepareComposition()` fique invisível para a medição atual.

A proposta é registrar:

```text
PARALLAX_DRAW_REQUEST
↓
PARALLAX_PREPARE_START
↓
PARALLAX_PREPARE_END
↓
PARALLAX_DRAW_START
```

Assim teremos duas métricas independentes:

### A — preparação

```text
PREPARE_START → PREPARE_END
```

### B — renderização

```text
DRAW_START → DRAW_COMPLETE
```

Não é necessário eliminar o `prepareComposition()` de `drawFrame()`.

---

# 3. Dividir o desenho das três camadas

Dentro de `drawFrame()`, antes de cada `drawLayer()`:

```text
PARALLAX_LAYER_START index=0
PARALLAX_LAYER_END index=0
```

e:

```text
PARALLAX_LAYER_START index=1
PARALLAX_LAYER_END index=1
```

e:

```text
PARALLAX_LAYER_START index=2
PARALLAX_LAYER_END index=2
```

Cada `END` deve informar a duração.

Exemplo:

```text
PARALLAX_LAYER_END index=0 durationMs=8
PARALLAX_LAYER_END index=1 durationMs=12
PARALLAX_LAYER_END index=2 durationMs=7
```

Isso deve medir o tempo total de cada chamada:

```java
drawLayer(...)
```

sem alterar seu conteúdo.

---

# 4. Dividir `drawLayer()` internamente apenas se necessário

Se a primeira instrumentação mostrar que uma determinada camada está consumindo muito tempo, então podemos fazer uma segunda etapa.

Não quero instrumentar excessivamente de início.

Primeiro medir:

```text
layer 0
layer 1
layer 2
```

Se, por exemplo, aparecer:

```text
layer 0 = 5 ms
layer 1 = 8 ms
layer 2 = 380 ms
```

a investigação passa para aquela camada.

Nesse caso, somente então separar:

```text
cálculo do RectF
→ drawBitmap
```

---

# 5. Medir `unlockCanvasAndPost()` separadamente

Este é um ponto fundamental.

Atualmente:

```java
holder.unlockCanvasAndPost(canvas);
```

acontece antes de:

```text
PARALLAX_DRAW_COMPLETE
```

Portanto, precisamos de:

```text
PARALLAX_BEFORE_UNLOCK
```

imediatamente antes:

```java
holder.unlockCanvasAndPost(canvas);
```

e:

```text
PARALLAX_AFTER_UNLOCK
```

imediatamente depois.

Exemplo:

```text
PARALLAX_BEFORE_UNLOCK
PARALLAX_AFTER_UNLOCK durationMs=372
PARALLAX_DRAW_COMPLETE
```

Se isso acontecer, teremos evidência muito forte de que o atraso está relacionado ao `unlockCanvasAndPost()` / entrega do buffer ao sistema.

---

# 6. Manter `lockCanvas()` separado

A medição existente deve permanecer:

```text
PARALLAX_LOCK_CANVAS
PARALLAX_LOCK_CANVAS_SUCCESS
```

mas também seria útil registrar a duração:

```text
PARALLAX_LOCK_CANVAS_END durationMs=X
```

Assim teremos:

```text
DRAW_START
↓
LOCK_CANVAS
↓
LOCK_CANVAS_SUCCESS
↓
LAYER 0
↓
LAYER 1
↓
LAYER 2
↓
BEFORE_UNLOCK
↓
AFTER_UNLOCK
↓
DRAW_COMPLETE
```

---

# 7. Resultado que queremos obter

Idealmente, um único primeiro frame após acender a tela produzirá algo semelhante a:

```text
PARALLAX_VISIBILITY_CHANGED visible=true

PARALLAX_SENSOR_REGISTERED

PARALLAX_PREPARE_START
PARALLAX_PREPARE_END durationMs=2

PARALLAX_DRAW_START force=true

PARALLAX_LOCK_CANVAS
PARALLAX_LOCK_CANVAS_SUCCESS durationMs=4

PARALLAX_LAYER_START index=0
PARALLAX_LAYER_END index=0 durationMs=6

PARALLAX_LAYER_START index=1
PARALLAX_LAYER_END index=1 durationMs=7

PARALLAX_LAYER_START index=2
PARALLAX_LAYER_END index=2 durationMs=8

PARALLAX_BEFORE_UNLOCK
PARALLAX_AFTER_UNLOCK durationMs=370

PARALLAX_DRAW_COMPLETE durationMs=399
```

Nesse exemplo, a causa estaria praticamente identificada:

```text
unlockCanvasAndPost() ≈ 370 ms
```

Outro possível resultado:

```text
PREPARE_END durationMs=420
DRAW_START
...
```

Nesse caso, o problema estaria no carregamento/preparação dos bitmaps e o `DRAW_START` atual estava escondendo o custo.

Outro:

```text
layer 0 = 380 ms
layer 1 = 5 ms
layer 2 = 6 ms
unlock = 4 ms
```

Nesse caso, investigaríamos especificamente o bitmap da camada 0.

---

# 8. Não modificar nesta etapa

Não fazer ainda nenhuma destas alterações:

* não reduzir a frequência do sensor;
* não alterar `registerListener`;
* não mudar `HandlerThread`;
* não mudar `frameQueued`;
* não alterar `requestFrame()`;
* não alterar o filtro do parallax;
* não alterar `drawScale`;
* não alterar `RectF`;
* não reduzir resolução dos bitmaps;
* não remover `FILTER_BITMAP_FLAG`;
* não remover `recycle()`;
* não implementar cache novo;
* não alterar `unlockCanvasAndPost()`;
* não alterar o ciclo de vida de `onVisibilityChanged()`;
* não alterar a calibração do sensor.

Esta etapa deve ser **somente observacional**.

---

# 9. Critério de sucesso

Após instalar a versão instrumentada, executar apenas:

1. deixar o Parallax Wallpaper ativo;
2. usar normalmente o celular;
3. apagar a tela;
4. esperar alguns segundos;
5. acender a tela;
6. não abrir o aplicativo Parallax Wallpaper;
7. repetir algumas vezes.

O objetivo é capturar especificamente o primeiro frame depois de:

```text
visible=false
→
visible=true
```

Não é necessário abrir o aplicativo.

---

# 10. Comando de captura

Depois da instalação da versão instrumentada:

```powershell
adb logcat -c
```

Em seguida:

```powershell
adb logcat -v threadtime --pid=30987 | Select-String "ParallaxWallpaper"
```

Se o PID mudar depois da instalação, primeiro obter o novo PID:

```powershell
adb shell pidof com.parallaxwallpaper.app
```

e substituir `30987` pelo PID retornado.

---

# Resultado esperado desta etapa

A pergunta que queremos responder é exclusivamente:

> **Dos aproximadamente 400 ms do primeiro frame após a retomada, quantos milissegundos são gastos em preparação dos bitmaps, quantos no desenho de cada camada e quantos em `unlockCanvasAndPost()`?**

Somente depois dessa medição devemos decidir qual alteração de desempenho faz sentido.
